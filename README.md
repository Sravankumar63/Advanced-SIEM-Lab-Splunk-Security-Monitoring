# Advanced SOC Lab: Security Monitoring, Detection & Incident Investigation Using Splunk

A hands-on Security Operations Center (SOC) laboratory built with VMware Workstation, Kali Linux, Windows 11, Ubuntu Server, and Splunk Enterprise. The project demonstrates an end-to-end SIEM workflow: endpoint log collection, controlled security-event generation, detection searches, alerting, investigation, and dashboard visualization.

## Project objectives

- Centralize Windows endpoint events in Splunk Enterprise.
- Configure Splunk Universal Forwarder (UF) to send Windows logs to the SIEM.
- Detect and investigate failed authentication, network reconnaissance, web SQL injection, and PowerShell activity.
- Build Splunk searches and alerts for repeatable detection.
- Present monitoring results in a SOC dashboard.

## Lab architecture

| System | Role | Lab address |
|---|---|---|
| Kali Linux 2026.2 | Security testing / Nmap source | `192.168.196.130` |
| Windows 11 Pro (Build 26200) | Monitored endpoint; XAMPP, Apache, DVWA | `192.168.196.128` |
| Ubuntu Server 26.04.1 LTS | Central SIEM server | `192.168.196.132` |

The VMs use a VMware custom network in the `192.168.196.0/24` range. Splunk Enterprise 10.4.3 runs on Ubuntu Server; Splunk Universal Forwarder 10.4.3 runs on Windows. The Splunk Web interface is available in the lab at `http://192.168.196.132:8000`, and the receiving port is TCP `9997`.

> These IP addresses are specific to the isolated lab and will differ in other environments. Do not expose lab services to the public internet.

## Technology stack

- **Virtualization:** VMware Workstation
- **SIEM:** Splunk Enterprise 10.4.3
- **Log forwarding:** Splunk Universal Forwarder 10.4.3
- **Endpoint / event sources:** Windows Security, Application, System, and PowerShell Operational logs
- **Network testing:** Kali Linux, Nmap
- **Web testing target:** DVWA hosted through XAMPP with Apache and MySQL
- **Analysis:** Splunk Search Processing Language (SPL), alerts, Dashboard Studio

## Implemented detection use cases

| Use case | Evidence / event source | Purpose |
|---|---|---|
| Failed Windows logons | Windows Security Event ID **4625** | Identify failed authentication attempts and review account, time, and source fields. |
| Network reconnaissance | Nmap `-sV` and `-sS`; Windows Filtering Platform Event ID **5156** where collected | Review scan activity and observed source/target/port patterns. |
| Web SQL injection | Apache access log generated by a controlled DVWA SQL injection test | Search web requests for SQL-injection indicators and investigate the request evidence. |
| PowerShell activity | PowerShell Operational Event ID **4104** | Verify collection and inspect logged PowerShell script-block activity. |

Testing was performed in a controlled virtual lab. Source addresses in logs must be interpreted in context: the documented DVWA request was generated locally on Windows and appeared with source `::1`; it should not be misrepresented as originating from Kali.

## Splunk alerts

The project report documents these configured alerts:

- `Nmap Network Reconnaissance Detection`
- `Windows Failed Login - Threshold Detection`
- `Windows Failed Login Detection`
- `Nmap SYN Scan Detection`
- `Web SQL Injection Detection`

Alert execution and notification behavior depend on the saved search schedule and alert actions configured in the lab.

## Dashboard

The Splunk Dashboard Studio dashboard is named **SOC Security Monitoring Dashboard**. It brings together failed-login activity, top source IPs, event sources, total security events, detected attacks, alert counts, activity over time, recent events, and web-attack evidence. Dashboard values are based on collected events and the selected time range.

## Reproducing the lab

1. Create an isolated VMware network and provision the three VMs listed above.
2. Install Splunk Enterprise on Ubuntu and enable a receiving port on TCP 9997.
3. Install Splunk Universal Forwarder on Windows and configure its output to `192.168.196.132:9997`.
4. Enable and verify the required Windows event inputs, including PowerShell Operational logging.
5. Generate only controlled test events in the lab, then validate ingestion in Splunk before writing detection searches.
6. Save searches and alerts, build the dashboard, and record evidence with timestamps and event details.

See the linked documentation for example commands and searches. Paths, indexes, sourcetypes, and field extractions can vary by Splunk input configuration; adjust searches to match the actual data in your environment.

## Safety and scope

This is an educational lab, not a production SOC deployment. Perform scans and web-application tests only against systems you own or are explicitly authorized to test. Do not publish passwords, tokens, private keys, personal event data, or unredacted screenshots containing sensitive information.
